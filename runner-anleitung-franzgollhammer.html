Runner für franzgollhammer starten.

Schritt für Schritt einen Runner-Container aus diesem Repository für franzgollhammer/franzgollhammer starten: Token anlegen, registrieren, mit einem Test-Workflow prüfen und wieder abbauen.

Grundlage ist main nach dem Merge von Pull Request #2 (fb7eed6). Die Ausgangslage wurde am 2. November 2026 geprüft: Das Ziel-Repository ist öffentlich, enthält nur README.md und assets/, hat keine Workflows und keinen registrierten Runner. Die Fork-Freigabe steht auf first_time_contributors. Docker läuft auf dem Mac über OrbStack (arm64, 8 CPUs, rund 4,9 GB RAM).

Öffentliches Repository: nur als bewusster, begrenzter Test.

Ein selbst gehosteter Runner führt aus, was die Workflows des Repositories verlangen. Bei einem öffentlichen Repository kann ein Pull Request aus einem Fork den Workflow ändern und damit Code auf deinem Rechner ausführen. Der Job hat im Container sudo und erreicht alles, was der Mac im Netz erreicht. Die README empfiehlt selbst gehostete Runner deshalb nur für private Repositories.

Diese Anleitung sichert das so weit wie möglich ab (Schritt 03 und 07) und baut den Runner am Ende wieder ab (Schritt 09). Für dauerhafte CI dieses Repositories reichen GitHub-gehostete Runner; bei öffentlichen Repositories sind sie kostenlos.

01Ausgangslage und Entscheidung

Persönliche Konten haben keine kontoweiten Runner. Ein Runner gehört deshalb immer zu genau einem Repository, hier zu franzgollhammer/franzgollhammer. Ohne Workflow, der ihn anfordert, wartet er nur.

Drei Wege für dieses Repository
WegVorteileNachteile
A: Kein eigener Runner, ubuntu-latestKostenlos bei öffentlichen Repositories, kein Risiko für eigene Rechner, x64Keine Kontrolle über die Hardware
B: Runner-Container auf dem MacSchnell eingerichtet, alles vorhandenÖffentliches Repository, arm64 statt x64, Jobs teilen sich einen Container, läuft nur, solange der Mac läuft
C: Runner auf einem eigenen Linux-ServerDauerbetrieb, x64, frischer Container pro Job über die systemd-UnitGleiches Risiko durch Fork-Pull-Requests, Einrichtung auf dem Server

Diese Anleitung beschreibt Weg B als Test. Für Weg C gelten dieselben Schritte; statt docker compose up startet dort die Unit aus systemd/actions-runner@.service den Runner (siehe README).

Voraussetzungen

  • Docker läuft: docker info antwortet ohne Fehler.
  • Die GitHub CLI ist angemeldet (gh auth status), und dein Konto ist Admin des Ziel-Repositories.
  • Dieses Repository ist ausgecheckt, die Befehle laufen in seinem Hauptordner, etwa ~/dev/ci-runner.

02Token anlegen

Der Runner tauscht beim Start ein Zugriffstoken gegen ein kurzlebiges Registrierungstoken und beim Stoppen gegen ein Entfernungstoken. Dafür braucht er ein Token, das genau dieses Repository verwalten darf.

  1. Unter Fine-grained personal access token erstellen einen Namen wie runner-franzgollhammer vergeben.
  2. Expiration: kurz halten, für einen Test etwa sieben Tage.
  3. Repository access: Only select repositories, dann franzgollhammer/franzgollhammer.
  4. Permissions: Repository permissions → Administration: Read and write. Metadata: Read setzt GitHub automatisch.
  5. Token erzeugen und kopieren. Es beginnt mit github_pat_.

Nicht das Token der GitHub CLI verwenden. gh auth token gilt für alle deine Repositories. Ein Job kann das Token im Container lesen, und bei einem öffentlichen Repository wäre das ein Zugang zu allen deinen Repositories.

Alternative für einen einzelnen Test

Ohne eigenes Token geht es mit einem Registrierungstoken, das die GitHub CLI holt. Es gilt eine Stunde. Danach kann sich der Runner weder abmelden noch nach einem Job neu registrieren; ein ephemerer Runner schafft so ungefähr einen Job.

Terminal

gh api -X POST repos/franzgollhammer/franzgollhammer/actions/runners/registration-token --jq .token

Den Wert dann in Schritt 04 als RUNNER_TOKEN statt ACCESS_TOKEN eintragen.

03Repository absichern

GitHub lässt Workflows aus Fork-Pull-Requests derzeit nur bei Erstbeitragenden auf eine Freigabe warten. Mit all_external_contributors wartet jeder Lauf von außen, bis du ihn freigibst.

Terminal

gh api -X PUT repos/franzgollhammer/franzgollhammer/actions/permissions/fork-pr-contributor-approval \
  -f approval_policy=all_external_contributors

gh api repos/franzgollhammer/franzgollhammer/actions/permissions/fork-pr-contributor-approval

Der zweite Befehl muss {"approval_policy":"all_external_contributors"} liefern. Dieselbe Einstellung findest du unter Settings → Actions → General → Approval for running fork pull request workflows from contributors.

Eine Freigabe schützt nur, wenn du vorher liest, was der Pull Request ändert. Gib keinen Lauf frei, der Dateien unter .github/workflows/ ändert oder ein runs-on mit self-hosted einführt.

04Env-Datei anlegen

Jede Runner-Gruppe bekommt eine eigene Env-Datei. Sie enthält das Token und ist nur für dich lesbar. Git ignoriert *.env, und der Docker-Build sieht nur entrypoint.sh, also landet das Token weder im Repository noch im Image.

Terminal

cd ~/dev/ci-runner
install -m 600 .env.example franzgollhammer.env

In franzgollhammer.env diese Werte setzen:

GITHUB_URL=https://github.com/franzgollhammer/franzgollhammer
ACCESS_TOKEN=github_pat_…
RUNNER_LABELS=containerized
RUNNER_NAME_PREFIX=docker
EPHEMERAL=true
RUNNER_CPUS=2
RUNNER_MEMORY=4g
  • EPHEMERAL=true: ein Job pro Registrierung, danach ein leeres Arbeitsverzeichnis.
  • RUNNER_MEMORY=4g passt in die rund 4,9 GB der OrbStack-VM. Mehrere Runner parallel brauchen kleinere Werte oder mehr VM-Speicher.
  • Kein COMPOSE_FILE eintragen. compose.docker.yml gibt Jobs den Docker-Socket des Hosts, und das ist Root-Zugriff auf den Docker-Host. Bei einem öffentlichen Repository kommt das nicht in Frage.

05Runner starten

Der Projektname -p franzgollhammer trennt diese Runner-Gruppe von anderen. Gib beides bei jedem Compose-Befehl mit: Ohne -p findet Compose die Container nicht, ohne --env-file fehlt GITHUB_URL.

Terminal

docker compose -p franzgollhammer --env-file franzgollhammer.env up -d --build
docker compose -p franzgollhammer --env-file franzgollhammer.env logs -f

Das Log meldet zuerst die Registrierung mit Labels und ephemeral: true und endet mit Listening for Jobs. Mit Ctrl+C verlässt du das Log; der Runner läuft weiter.

06Registrierung prüfen

Terminal

gh api repos/franzgollhammer/franzgollhammer/actions/runners \
  --jq '.runners[] | {name, status, labels: [.labels[].name]}'

Erwartet wird ein Runner namens docker-<Container-ID> mit Status online und den Labels self-hosted, Linux, ARM64 und containerized. Auf einem x64-Server steht dort X64 statt ARM64. Im Browser zeigt Settings → Actions → Runners dasselbe.

07Test-Workflow anlegen

Ein Job landet auf einem Runner, der alle Labels aus runs-on trägt. Der folgende Workflow gehört ins Ziel-Repository franzgollhammer/franzgollhammer, nicht in dieses.

.github/workflows/runner-smoke.yml

name: Runner smoke test

on:
  workflow_dispatch:
  push:
    branches: [ci/runner-smoke]

permissions:
  contents: read

jobs:
  smoke:
    runs-on: [self-hosted, linux, containerized]
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - run: |
          echo "Runner: $RUNNER_NAME"
          uname -m
          ls -la
  • Kein pull_request-Trigger und erst recht kein pull_request_target. So starten nur deine eigenen Pushes und manuelle Läufe einen Job auf dem Runner.
  • permissions: contents: read beschränkt das GITHUB_TOKEN des Jobs auf Lesen.
  • workflow_dispatch lässt sich erst starten, wenn die Datei auf dem Standard-Branch liegt. Für den ersten Test startet deshalb ein Push auf den Branch ci/runner-smoke den Lauf.

Terminal

gh repo clone franzgollhammer/franzgollhammer ~/dev/franzgollhammer
cd ~/dev/franzgollhammer
git switch -c ci/runner-smoke
mkdir -p .github/workflows
# runner-smoke.yml mit dem Inhalt oben anlegen
git add .github/workflows/runner-smoke.yml
git commit -m "Add self-hosted runner smoke test"
git push -u origin ci/runner-smoke

08Lauf beobachten

Terminal

gh run list -R franzgollhammer/franzgollhammer --workflow runner-smoke.yml --limit 3
gh run watch -R franzgollhammer/franzgollhammer

# im Ordner von ci-runner
docker compose -p franzgollhammer --env-file franzgollhammer.env logs -f

Der Job sollte sofort starten und aarch64 ausgeben. Danach passiert Folgendes:

  1. GitHub entfernt die Registrierung des ephemeren Runners, der Prozess im Container endet.
  2. Compose startet denselben Container neu (restart: unless-stopped).
  3. Der Entrypoint leert das Arbeitsverzeichnis, holt mit ACCESS_TOKEN ein neues Registrierungstoken und meldet einen frischen Runner an.

Derselbe Container, nicht ein neuer. Nur das Arbeitsverzeichnis wird geleert. Was ein Job sonst im Container ändert, etwa mit sudo installierte Pakete, bleibt für den nächsten Job erhalten. Einen frischen Container pro Job gibt es nur mit der systemd-Unit auf Linux (Weg C).

Mit RUNNER_TOKEN statt ACCESS_TOKEN scheitert die Neuregistrierung, sobald das Token abgelaufen ist; der Container startet dann immer wieder neu. Nach dem Test also gleich mit Schritt 09 weitermachen.

09Abbauen

down stoppt den Container. Mit ACCESS_TOKEN meldet der Entrypoint den Runner dabei innerhalb von 90 Sekunden bei GitHub ab. Mit RUNNER_TOKEN bleibt er als offline stehen; dann unter Settings → Actions → Runners von Hand löschen.

Terminal

docker compose -p franzgollhammer --env-file franzgollhammer.env down

gh api repos/franzgollhammer/franzgollhammer/actions/runners --jq .total_count

Der zweite Befehl muss 0 liefern. Danach aufräumen:

  • Token unter Fine-grained personal access tokens löschen, wenn kein Runner mehr folgt.
  • Env-Datei löschen: rm franzgollhammer.env.
  • Test-Branch im Ziel-Repository löschen: git push origin --delete ci/runner-smoke.
  • Die strengere Fork-Freigabe aus Schritt 03 kann bleiben; sie schadet auch ohne Runner nicht.
