Technischer Bericht · 2. November 2026

Docker-Runner verstehen.

Vom Image-Bau über die Registrierung bei GitHub bis zum Job-Ende: So arbeiten die selbst gehosteten GitHub-Actions-Runner dieses Repositories.

Grundlage ist main mit dem Merge von Pull Request #1 (93e7445), also der Stand nach den Review-Fixes. Dieser Bericht erklärt die Konfiguration im Repository; er ist kein Nachweis über ein aktuell laufendes Deployment.

GitHub verteilt die Arbeit. Dein Host führt sie aus. Der Runner verbindet sich mit GitHub, übernimmt passende Jobs und meldet Ergebnisse zurück. Docker stellt die Laufzeitumgebung bereit. Das Entrypoint-Script automatisiert Registrierung und Abmeldung.

01Welche Teile zusammenspielen

Ein Workflow besteht aus Jobs. GitHub verarbeitet Ereignisse wie Push, Pull Request oder manuellen Start, berücksichtigt Job-Abhängigkeiten und sucht einen verfügbaren Runner. Der Runner ist das Programm, das den zugewiesenen Job tatsächlich ausführt.

Die Rechenlast liegt auf deinem Host. GitHub bleibt für die Workflow-Steuerung zuständig. Deshalb bleiben Tests, die über diesen Runner laufen, reguläre GitHub-Actions-Jobs.

Die zentralen Dateien
DateiVerantwortung
DockerfileBasisimage, Zusatzpakete, Benutzer und Entrypoint
compose.yamlContainerstart, Umgebung, Ressourcenlimits, Neustart und Logs

02Vom Image zum laufenden Container

Das Dockerfile verwendet das offizielle Image ghcr.io/actions/actions-runner. Die aktuelle Datei fixiert Version 2.338.2 zusätzlich über einen SHA-256-Digest. Damit ist die verwendete Image-Basis eindeutig festgelegt.

FROM ghcr.io/actions/actions-runner:2.338.2@sha256:759a1d94a15b05941aba5196974ff43fe15b4cbba29b694b35cbc32a1166b232

Das Basisimage enthält Ubuntu 24.04, den GitHub-Runner, Git, curl, jq, Docker CLI und Buildx. Der Benutzer runner hat UID 1001 und passwortloses sudo. Dein Dockerfile ergänzt tini, optionale APT-Pakete und das eigene Entrypoint-Script. [1]

Ein Image ist eine Vorlage; ein Container ist eine Instanz dieser Vorlage. Mehrere Container können dasselbe Image verwenden. Jeder Container besitzt eine eigene beschreibbare Dateisystemschicht, solange er nicht ausdrücklich gemeinsame Hostverzeichnisse oder Volumes einbindet.

Ein Start mit folgendem Befehl baut das Image und erstellt beziehungsweise aktualisiert den Compose-Dienst:

docker compose up -d --build

--build baut unter Nutzung des vorhandenen Build-Caches. -d startet im Hintergrund. Die Werte aus .env werden für die Variablenersetzung in Compose verwendet und die dort aufgeführten Umgebungsvariablen an den Container übergeben.

Die Startkette lautet:

tini (PID 1)
  └─ /usr/local/bin/entrypoint.sh
       └─ ./run.sh
            └─ Runner-Listener und Job-Worker

tini reicht Stoppsignale weiter und sammelt verwaiste Prozesse ein. Der Entrypoint läuft in /home/runner und bereitet dort die Registrierung vor.

Linux bleibt Linux. Auf einem Mac läuft dieses Image in einer Linux-VM. Der Runner meldet sich deshalb als Linux-Runner. Native macOS-Tests benötigen einen eigenen macOS-Runner.

Die Werkzeugausstattung entspricht außerdem nicht automatisch einem kompletten GitHub-gehosteten ubuntu-latest-System. Benötigte Node-, Python-, Browser- oder Compiler-Abhängigkeiten müssen das Image oder der jeweilige Workflow bereitstellen.

03Wie die Registrierung funktioniert

Das Ziel bestimmt den Geltungsbereich

Der Entrypoint liest und prüft GITHUB_URL. Er entfernt einen abschließenden Schrägstrich beziehungsweise das Suffix .git und leitet daraus den API-Pfad ab.

Registrierungsziele
URL-MusterAPI-Geltungsbereich
https://github.com/owner/repoRepository: repos/owner/repo
https://github.com/orgOrganisation: orgs/org
https://github.com/enterprises/nameEnterprise: enterprises/name

Ein persönlicher Account hat keinen gemeinsamen Runner-Pool für alle eigenen Repositories. Eine URL mit nur einem Namen nach dem Host wird vom Script als Organisationsziel interpretiert.

Für GitHub.com verwendet das Script https://api.github.com. Bei GitHub Enterprise Server leitet es standardmäßig <host>/api/v3 ab. GITHUB_API_URL kann diese Vorgabe überschreiben. Ziel und API-Basis müssen HTTPS verwenden.

Vier verschiedene Token-Aufgaben

Authentifizierung und Berechtigungen
TokenAufgabe
ACCESS_TOKENAuthentifiziert API-Aufrufe, die Registrierungs- und Entfernungstoken erzeugen.
RUNNER_TOKENErlaubt die Registrierung. Kann direkt übergeben oder per API beschafft werden.
EntfernungstokenErlaubt config.sh remove, um die Registrierung zu entfernen.
GITHUB_TOKENWird von GitHub pro Job für Zugriffe aus dem Workflow erzeugt.

Mit ACCESS_TOKEN fordert der Entrypoint beispielsweise folgendes Registrierungstoken an:

POST https://api.github.com/repos/<owner>/<repo>/actions/runners/registration-token
Authorization: Bearer <ACCESS_TOKEN>

Im tatsächlichen Aufruf liest curl den Authorization-Header von der Standardeingabe. Das Verwaltungstoken steht dadurch nicht als Argument in der Kommandozeile. Verbindungs-, Laufzeit- und Wiederholungsgrenzen begrenzen die Wartezeit auf die API.

Der Entrypoint wertet den HTTP-Status der Antwort aus. Bei 401, 404 oder 403 ohne Rate-Limit-Hinweis ist das Token falsch, ohne Berechtigung oder das Ziel falsch; ein späterer Versuch würde genauso scheitern. Der Container endet dann mit Exit-Status 78. Bei 5xx, 429, einem Rate-Limit oder einem Netzwerkfehler endet er mit 1, und ein Neustart darf es erneut versuchen.

Die API liefert ein Token mit einer Stunde Gültigkeit. Ein Fine-grained PAT braucht für Repository-Runner Administration: write; bei Organisationsrunnern ist die relevante Organisationsberechtigung Self-hosted runners: write. [2]

Nach der Registrierung beendet der Ablauf dieses Tokens keinen laufenden Runner. Der konfigurierte Runner verwendet seine eigene Identität für die Verbindung zum Actions-Dienst. Ein neues Registrierungstoken wird beim nächsten Registrierungsdurchlauf benötigt.

Ein direkt übergebenes RUNNER_TOKEN ist deshalb für einen dauerhaft neu startenden ephemeren Pool unpraktisch: Nach dem Ablauf kann es keine weitere Registrierung ermöglichen. ACCESS_TOKEN kann frische Token anfordern, solange es selbst gültig bleibt und ausreichende Rechte besitzt.

Name, Labels und lokale Zugangsdaten

Ohne festen RUNNER_NAME verwendet das Script <RUNNER_NAME_PREFIX>-<HOSTNAME>, standardmäßig also etwa docker-abc123. Beim normalen Docker-Start entspricht der Hostname dem kurzen Container-Identifier.

ACTIONS_RUNNER_INPUT_TOKEN=<registration-token> ./config.sh \
  --unattended \
  --replace \
  --url https://github.com/<owner>/<repo> \
  --name docker-abc123 \
  --work _work \
  --labels containerized \
  --ephemeral

--unattended verhindert Rückfragen. --replace ersetzt eine vorhandene Registrierung gleichen Namens. --ephemeral begrenzt die Registrierung auf einen Job. Runner-Gruppe, Standardlabels und Selbstupdate werden bei Bedarf durch weitere Argumente gesteuert.

Das Registrierungstoken erhält config.sh über die Umgebungsvariable ACTIONS_RUNNER_INPUT_TOKEN. Es wird nicht als Kommandozeilenargument übergeben. Vor einer neuen Einrichtung entfernt das Script lokale Alt-Konfiguration mit config.sh remove --local, einschließlich migrierter Runner-Dateien.

config.sh läuft dabei im Hintergrund, und der Entrypoint wartet darauf. Bash würde ein Stoppsignal sonst erst nach dem Ende von config.sh bearbeiten, und config.sh wiederholt Verbindungsversuche minutenlang, wenn GitHub nicht erreichbar ist. So beendet ein Stopp auch eine laufende Registrierung sofort. Lehnt config.sh ein direkt übergebenes RUNNER_TOKEN ab, endet der Container mit 78: Dieses Token wird mit der Zeit nur älter.

Ein Sonderfall erhält eine bestehende Registrierung: Fehlt ACCESS_TOKEN und liegt im selben Container noch .runner vor, verwendet der Entrypoint diese Registrierung weiter. So kann ein bestehender Runner auch mit inzwischen abgelaufenem Registrierungstoken erneut starten. Nach einem abgeschlossenen ephemeren Job fehlt diese Registrierung; dann wird wieder ein gültiges Token benötigt.

Der Runner speichert Metadaten und Zugangsdaten in Dateien wie .runner, .credentials und .credentials_rsaparams. Bei seiner Konfiguration entsteht ein Schlüsselpaar; die eigene Runner-Identität ermöglicht später den Zugriff auf die Jobnachrichten. [3]

Die tatsächlichen Argumente und der Token-Austausch stehen in entrypoint.sh. Ein fester Runnername ist nur für eine einzelne Instanz geeignet.

04Vom wartenden Runner zum fertigen Job

Der Runner holt seine Aufträge

Nach der Einrichtung startet run.sh den Listener. Dieser authentifiziert sich beim Actions-Dienst und wartet auf Jobnachrichten. Die Verbindung wird vom Runner aus aufgebaut; die Warteschlange wird über HTTP-Anfragen mit langer Wartezeit abgefragt. [3]

Für die Jobannahme ist kein eingehender Port nötig. Ausgehend braucht der Host HTTPS über Port 443 sowie Zugriff auf die für Actions, Downloads und Artefakte verwendeten Dienste. Die Meldung Listening for Jobs zeigt an, dass der Listener auf Arbeit wartet. [4]

Alle angeforderten Labels müssen passen

Ein Workflow im Zielrepository kann den Runner so auswählen. ./run-tests.sh steht hier beispielhaft für den Testbefehl dieses Zielprojekts:

jobs:
  test:
    runs-on: [self-hosted, linux, containerized]
    steps:
      - uses: actions/checkout@v7
      - run: ./run-tests.sh

Der Runner muss alle Labels aus runs-on besitzen. Die Standardlabels beschreiben self-hosted, Betriebssystem und Architektur, etwa Linux und X64 oder ARM64. Eigene Labels kommen aus RUNNER_LABELS. Labelnamen werden ohne Beachtung der Groß-/Kleinschreibung verglichen. [5]

GitHub weist den Job einem passenden freien Runner zu. Fehlt ein solcher Runner, bleibt der Job in der Warteschlange; nach 24 Stunden ohne passenden Runner schlägt er fehl. Ein automatischer Wechsel zu einem GitHub-gehosteten Runner ist nicht vorgesehen. [4]

Der Worker führt die Steps aus

  1. Job übernehmenDer Listener startet einen Worker für den zugewiesenen Job.
  2. Arbeitsumgebung vorbereitenDer Worker lädt benötigte Actions. Ein Checkout findet statt, wenn der Workflow einen entsprechenden Step enthält.
  3. Steps ausführenShellbefehle, Setup-Actions, Installationen, Tests und Builds laufen in der vom Workflow festgelegten Reihenfolge.
  4. Nachbereitung und ErgebnisPost-Schritte laufen nach ihren Bedingungen; Status und Logs werden an GitHub übertragen.

Normale run:-Steps sind Prozesse im Runner-Container unter Benutzer runner. Sie teilen Arbeitsdateien, starten aber jeweils eine eigene Shell. Ein cd oder eine nur in der Shell gesetzte Variable wird deshalb nicht automatisch in den nächsten Step übernommen.

GitHub erzeugt für jeden Job ein eigenes GITHUB_TOKEN. Seine Rechte werden durch Repository-, Organisations- und Workflow-Einstellungen begrenzt. Dieses Token ist vom Runner-Verwaltungstoken unabhängig. [6]

Jobausgaben erscheinen in GitHub Actions. Beliebige Dateien aus dem Arbeitsverzeichnis werden nicht automatisch zu dauerhaften Artefakten: Dafür muss der Workflow ausdrücklich Upload- beziehungsweise Cache-Actions verwenden.

05Was nach einem Job erhalten bleibt

Compose setzt standardmäßig EPHEMERAL=true. Eine solche Runner-Registrierung verarbeitet einen Job. GitHub entfernt sie danach; die Bereinigung und Wiederbereitstellung der Umgebung übernimmt deine Automatisierung. [4]

Für den nächsten Durchlauf gibt es zwei Betriebsweisen: docker compose up startet denselben Container erneut; der optionale systemd-Dienst erstellt jeweils einen neuen Container. Der folgende Ablauf beschreibt zunächst compose up.

Ephemere Registrierung, weiterverwendeter Container

EPHEMERAL=true liefert hier ein frisches Arbeitsverzeichnis. Die übrige beschreibbare Containerschicht bleibt bei einem Neustart erhalten. Das ist die wichtigste Grenze dieser Umsetzung.

Zustand nach einem normalen ephemeren Durchlauf
BereichVerhalten
Runner-RegistrierungWird für den nächsten Durchlauf neu eingerichtet.
ArbeitsverzeichnisWird beim nächsten Start gelöscht und neu angelegt, auch nach einem vorherigen Absturz.
Absolutes Host-ArbeitsverzeichnisDer Unterordner dieses Runners wird bei jedem Ende des Entrypoints entfernt, auch nach einem Fehler beim Start. Nur bei einem harten Abbruch (SIGKILL) können Reste bleiben.
Home-Dateien außerhalb des ArbeitsverzeichnissesBleiben im selben Container erhalten.
/tmp und mit sudo installierte PaketeBleiben im selben Container erhalten.
Images, Volumes und Build-Caches im Host-DockerBleiben unabhängig vom Runner-Container erhalten.

Mit EPHEMERAL=false wartet der Runner nach einem Job auf den nächsten. Registrierung und Arbeitsverzeichnis bleiben während dieser Laufzeit bestehen. Beim tatsächlichen Containerneustart erfolgt normalerweise eine neue Registrierung; ohne Verwaltungstoken wird eine vorhandene Registrierung weiterverwendet. Ein absolutes Arbeitsverzeichnis wird auch im persistenten Modus bei jedem Ende des Entrypoints entfernt.

docker compose up -d --force-recreate erstellt einen neuen Container und setzt damit dessen beschreibbare Schicht zurück. Bind-Mounts und Host-Docker-Zustand bleiben bestehen. Nach harten Abbrüchen können alte Runner-Unterverzeichnisse auf dem Host zurückbleiben.

Ein fehlgeschlagener Test ist außerdem nicht gleichbedeutend mit einem defekten Runner. Das Testergebnis wird in GitHub gemeldet; der ephemere Lebenszyklus kann anschließend regulär weitergehen.

Ein neuer Container pro Job über systemd

Die Vorlage systemd/actions-runner@.service verwendet einen einmaligen Compose-Aufruf. Der Container nimmt einen Job an und wird danach durch --rm entfernt. -e EPHEMERAL=true erzwingt diesen Modus, auch wenn die Env-Datei etwas anderes sagt:

docker compose -p <instanz> --env-file <instanz>.env \
  run --build --rm -T -e EPHEMERAL=true --name <instanz>-runner runner

systemd startet nach fünf Sekunden den nächsten Durchlauf aus dem Image. Dadurch werden Home-Dateien, /tmp, nachinstallierte Pakete und jede Änderung am Runner selbst in der beschreibbaren Containerschicht verworfen. Host-Bind-Mounts, Images, Volumes und Host-Build-Caches bleiben davon unabhängig. Mit dem Docker-Override gilt die Trennung deshalb nicht: Ein Job kann über den Socket den Host verändern, auch das Repository unter /opt/actions-runner-docker, aus dem jeder spätere Container gebaut wird.

docker compose run reicht Stoppsignale nicht an den Container weiter. Der Dienst stoppt den benannten Container deshalb selbst mit ExecStop=docker stop -t 90; der Entrypoint meldet den Runner dann ab. Vor jedem Start prüft ExecCondition mit docker compose config -q, ob Env-Datei und Pflichtwerte vorhanden sind. Fehlen sie, bleibt der Dienst gestoppt statt alle fünf Sekunden in denselben Fehler zu laufen. Dasselbe bewirkt RestartPreventExitStatus=78 für Einstellungen, die nicht funktionieren können, und für Token, die GitHub ablehnt.

Die Dienstvorlage erwartet das Repository unter /opt/actions-runner-docker und eine zum Instanznamen passende Env-Datei. Ein anderer Ablageort benötigt ein angepasstes WorkingDirectory. Der Dienst braucht ACCESS_TOKEN, weil ein RUNNER_TOKEN höchstens für eine Registrierung reicht. Docker-Jobs schaltet die Env-Datei einer Instanz mit COMPOSE_FILE=compose.yaml:compose.docker.yml ein; die gemeinsame Vorlage bleibt unverändert. Ein eventuell nach einem Absturz zurückgebliebener Container mit dem festen Instanznamen wird vor dem Start entfernt.

06Wie Docker innerhalb eines Jobs funktioniert

Im Basis-Setup ist zwar die Docker CLI installiert, aber kein Daemon für die Jobs verbunden. Deshalb funktionieren Docker-Builds, Docker-Container-Actions und Service-Container erst mit einer zusätzlichen Daemon-Anbindung.

Das optionale Override wird pro Runner-Set in dessen Env-Datei eingeschaltet. Das wirkt für docker compose und für den systemd-Dienst gleichermaßen:

COMPOSE_FILE=compose.yaml:compose.docker.yml
DOCKER_GID=<gruppe von /var/run/docker.sock>

DOCKER_GID muss zur Gruppe des Host-Sockets passen. Auf einem Linux-Host ermittelt stat -c %g /var/run/docker.sock diese Gruppen-ID. Das Override ergänzt diese Gruppe für den Benutzer im Container. Mit COMPOSE_FILE lädt Compose ein lokales compose.override.yaml nicht mehr von selbst; wer darüber eine Token-Datei einbindet, hängt es an die Liste an.

Der Host-Daemon erstellt weitere Container

Das Override bindet /var/run/docker.sock ein. Docker-Befehle im Runner werden dadurch vom Host-Daemon ausgeführt. Zusätzliche Container laufen als Geschwister des Runner-Containers auf demselben Docker-Host.

Docker-Host
├─ Runner-Container
├─ Testcontainer, den ein Job mit docker run startet
└─ Datenbankcontainer, den ein Job als Service benötigt

Diese Konfiguration betreibt keinen eigenen Docker-Daemon im Runner. Sie ergänzt die Hostadresse host.docker.internal und gibt den Runnern nur die Labels aus RUNNER_DOCKER_LABELS, standardmäßig nur docker. Weder RUNNER_LABELS noch die Standardlabels self-hosted, Linux und X64 sind gesetzt. Jobs fordern diese Runner deshalb ausdrücklich an:

runs-on: docker

Warum Host und Runner denselben Pfad brauchen

Bei einem Bind-Mount interpretiert der Daemon den Quellpfad auf seinem eigenen Host. Ein Pfad, der nur im Runner-Container existiert, reicht daher nicht aus. [7]

docker run --rm -v "$PWD:/src" <image>

Damit dieser Befehl die Checkout-Dateien findet, wird standardmäßig /var/lib/actions-runner/<compose-projekt> auf Host und Runner unter demselben absoluten Pfad eingebunden. Docker legt das Verzeichnis als root an. Die Projekte sind dadurch voneinander getrennt. Das Entrypoint-Script hängt zusätzlich pro Runner einen Unterordner mit Modus 700 an:

Host:    /var/lib/actions-runner/ucsl/docker-abc123/
Runner:  /var/lib/actions-runner/ucsl/docker-abc123/

Die Checkout-Verzeichnisse liegen wiederum darunter. RUNNER_DOCKER_WORKDIR kann den gemeinsamen Basispfad ändern. Ein eingebundenes Verzeichnis, in das andere Konten schreiben dürfen oder das weder root noch dem Runner gehört, lehnt der Entrypoint mit Exit-Status 78 ab: Sonst könnte ein anderes Konto auf dem Host das Runner-Verzeichnis gegen ein eigenes austauschen. Verschiedene Runnernamen trennen die Arbeitsverzeichnisse mehrerer Replikate. Bei jedem Ende räumt der Entrypoint den Unterordner dieses Runners auf.

Welche Workflow-Funktionen unterstützt sind

Unterstützung mit dem aktuellen Host-Socket-Override
FunktionStatus und Grenze
docker buildUnterstützt.
docker runUnterstützt; Bind-Mounts funktionieren für die gemeinsam verfügbaren Hostpfade.
Docker-Container-ActionsUnterstützt, etwa uses: docker://… und Dockerfile-Actions.
services:Unterstützt; veröffentlichte Service-Ports sind über den Host erreichbar.
Job mit container:Mit dieser Konfiguration nicht unterstützt: Weitere Runnerpfade fehlen auf dem Host.

Bei einem container:-Job will der Runner unter anderem /home/runner/externals in den Jobcontainer einbinden. Dieser Pfad existiert im aktuellen Setup nur im Runner-Container. Das README und der Kommentar im Docker-Override grenzen diese Funktion deshalb ausdrücklich aus.

Bei Services verweist localhost auf den Runner-Container. Ein Service veröffentlicht seinen Port auf dem Host, und der Runner erreicht ihn über host.docker.internal. Damit parallele Jobs nicht um denselben Hostport konkurrieren, wählt Docker den Port, und der Job liest ihn aus dem Kontext:

services:
  db:
    image: postgres:17
    ports: ["5432"]
steps:
  - run: psql -h host.docker.internal -p ${{ job.services.db.ports['5432'] }} ...

Veröffentlichte Ports sind auf allen Hostschnittstellen offen, und Dockers Regeln umgehen ufw. Der Host gehört deshalb hinter eine Firewall, die eingehenden Verkehr verwirft.

Die projektbezogene Unterstützung und ihre Grenzen stehen im Abschnitt „Docker in jobs“ der README.md.

07Ressourcen, Isolation und Secrets

Limits gelten für den Runner-Container

Compose begrenzt standardmäßig CPU-Zeit auf das Äquivalent von zwei CPUs und RAM auf 4g. Das ist keine Reservierung exklusiver CPU-Kerne. Normale Test- und Buildprozesse innerhalb des Runner-Containers teilen diese Limits.

Zusätzliche Container des Host-Daemons besitzen eigene Limits. Die CPU- und RAM-Grenzen des Runners begrenzen diese Geschwister-Container nicht automatisch. Diese Folgerung ergibt sich aus den getrennten Containern und den Ressourcenlimits pro Container. [8]

Docker-Socket bedeutet weitreichende Hostkontrolle

Ein Workflow mit Zugriff auf den Socket eines üblichen rootful Docker-Daemons kann privilegierte Container starten und Hostdateien einbinden. Damit erhält er praktisch Root-Kontrolle über den Docker-Host. Bei Docker Desktop läuft dieser Daemon in einer Linux-VM; freigegebene Dateien des Macs können ebenfalls betroffen sein.

Ein frisches Arbeitsverzeichnis ist keine vollständige Sicherheitsgrenze

Jobs laufen unter demselben Benutzer wie der Runner und können über passwortloses sudo den Container verändern. Solche Änderungen außerhalb des Arbeitsverzeichnisses überleben den nächsten Containerneustart. Mit Host-Socket können darüber hinaus Änderungen am Docker-Host bestehen bleiben.

Auch private Repositories können ungeprüfte Änderungen oder kompromittierte Abhängigkeiten enthalten. Für solche Jobs muss die Ausführungsgrenze zum tatsächlichen Vertrauensniveau passen. Eine getrennte Ausführungsmaschine oder Wegwerf-VM begrenzt andere Risiken als nur das Löschen eines Checkout-Verzeichnisses.

Token werden aus der Jobumgebung entfernt

Der Entrypoint startet den Runner mit folgender bereinigter Umgebung:

env -u ACCESS_TOKEN -u ACCESS_TOKEN_FILE \
    -u RUNNER_TOKEN -u RUNNER_TOKEN_FILE ./run.sh

Das reduziert versehentliche Weitergabe an Jobprozesse. Es schützt diese Secrets jedoch nicht zuverlässig vor absichtlich bösartigem Code im selben Container. Der Verwaltungszugang ist für den Entrypoint weiterhin verfügbar, und Jobs haben weitreichende Rechte im Container.

Außerhalb der Jobs steht das Token auf keiner Kommandozeile, die andere Konten des Hosts mit ps sehen könnten: curl liest es von der Standardeingabe, config.sh aus ACTIONS_RUNNER_INPUT_TOKEN.

.env und *.env sind in Git ignoriert. Die .dockerignore lässt ausschließlich entrypoint.sh in den Build-Kontext. Zugangstoken wird dadurch nicht in das Image kopiert. Es bleibt dennoch ein Laufzeit-Secret, dessen Rechte und Gültigkeit begrenzt werden müssen. Env-Dateien mit Token gehören nur dem Konto, das Compose startet (install -m 600 .env.example .env, chmod 600 *.env); sonst kann jedes Konto des Hosts das Token aus der Datei lesen.

Labels steuern Auswahl, keinen Ausschluss

Das Docker-Override trennt die Labels vollständig von denen normaler Runner: Seine Runner tragen nur docker, ohne containerized und ohne die Standardlabels. Weder ein Job mit containerized noch ein breites runs-on: [self-hosted, linux] landet dadurch versehentlich auf einem Runner mit Host-Socket.

Labels steuern trotzdem nur die Auswahl. Ein Workflow, der runs-on: docker verlangt, bekommt diesen Runner, ganz gleich, wer den Workflow geändert hat. Ein engerer Zugriff braucht passende Pool-, Repository- oder Runner-Gruppenregeln.

08Skalieren, stoppen und aktualisieren

Mehr Runner erlauben mehr gleichzeitige Jobs

docker compose up -d --scale runner=3

Drei Runner erlauben bis zu drei gleichzeitig zugewiesene Jobs, soweit Workflow-Abhängigkeiten und GitHub-Regeln das zulassen. Ein einzelner Job bleibt auf einem Runner; darin können Tests intern mehrere Prozesse starten.

Mit den Standardlimits können diese drei Runner zusammen CPU-Zeit entsprechend sechs CPUs und je bis zu 4g RAM beanspruchen. Zusätzliche Docker-Container kommen gegebenenfalls hinzu. Compose vergrößert oder verkleinert den Pool nicht selbst anhand der Jobwarteschlange.

Persönliche Repositories erhalten getrennte Runner-Sets. Eigene Compose-Projektnamen trennen die Dienste und Netzwerke:

docker compose -p ucsl --env-file ucsl.env up -d --build
docker compose -p dotagents --env-file dotagents.env up -d --build

Organisationen können einen gemeinsamen Pool registrieren und Repository-Zugriff über Runner-Gruppen steuern. Ein fest gesetztes RUNNER_NAME darf beim Skalieren nicht für alle Replikate identisch sein.

Sauberes Stoppen und Abmelden

Bei docker compose down sendet Docker ein Stoppsignal. tini reicht es an den Entrypoint weiter. Das Script signalisiert den Runner, wartet auf dessen Prozessende und versucht anschließend, eine noch vorhandene Registrierung zu entfernen. Kommt der Stopp während einer Registrierung, beendet das Script config.sh und räumt danach genauso auf.

POST <api-base>/<scope>/actions/runners/remove-token

ACTIONS_RUNNER_INPUT_TOKEN=<remove-token> ./config.sh remove

Hat sich ein ephemerer Runner bereits selbst entfernt, ist keine weitere Abmeldung nötig. Ohne ACCESS_TOKEN kann das Script kein Entfernungstoken beschaffen und lässt eine noch vorhandene Registrierung zurück.

Compose gibt dem Stoppen 90 Sekunden Zeit. Danach kann Docker hart beenden. Der systemd-Dienst verwendet ebenfalls docker stop -t 90 und hat zusätzlich TimeoutStopSec=120 für den gesamten Dienststopp. Damit die Abmeldung in diese Frist passt, sind die Token-Anfrage durch die curl-Grenzen und config.sh remove durch timeout 40 begrenzt. Diese Fristen garantieren nicht, dass ein laufender Job vollständig fertig wird. Ist GitHub in dieser Zeit nicht erreichbar, meldet das Log warning: could not remove, und der Runner bleibt als offline registriert zurück, bis GitHub ihn nach längerer Offline-Zeit selbst entfernt oder jemand ihn in den Einstellungen löscht.

restart: unless-stopped startet selbstständig beendete Container erneut. Ein ausdrücklich gestoppter Container bleibt gestoppt. [9]

Runner- und Image-Updates haben getrennte Aufgaben

Standardmäßig darf sich die Runner-Software selbst aktualisieren. Mit DISABLE_AUTO_UPDATE=true entfällt dies; dann muss ein ausreichend aktuelles Image bereitgestellt werden. GitHub verlangt bei ausgeschaltetem Selbstupdate Aktualisierung innerhalb von 30 Tagen nach einem neuen Release und kann kritische Sicherheitsupdates früher zur Voraussetzung weiterer Jobs machen. [4]

Dependabot prüft wöchentlich das Basisimage und die GitHub Actions dieses Repositories. Nach einer übernommenen Dockerfile-Änderung muss das Image neu gebaut und der Dienst entsprechend aktualisiert werden. Ein Selbstupdate des Runners pflegt keine Betriebssystempakete und eigenen Tools.

Fehlersuche beginnt bei Logs, Status und Labels

docker compose logs -f zeigt Start- und Registrierungsprobleme. Die Runner-Verwaltung auf GitHub zeigt Erreichbarkeit, Labels und Beschäftigung. Der konkrete Actions-Job zeigt Step-Ausgaben und Testergebnisse. Compose rotiert Containerlogs über den Treiber json-file mit bis zu drei Dateien zu je 10m.

09Die Konfiguration im Überblick

Die Vorlage .env.example enthält die konfigurierbaren Werte. Im folgenden Beispiel müssen Ziel und Token vor einem Start ersetzt werden:

GITHUB_URL=https://github.com/<owner>/<repo>
ACCESS_TOKEN=<token>
RUNNER_LABELS=containerized
RUNNER_NAME_PREFIX=docker
EPHEMERAL=true
RUNNER_CPUS=2
RUNNER_MEMORY=4g

Weil die Datei ein Token enthält, entsteht sie am besten gleich ohne Leserechte für andere: install -m 600 .env.example .env.

Zusätzlich unterstützt der Entrypoint ACCESS_TOKEN_FILE und RUNNER_TOKEN_FILE. Der Dateiinhalt hat Vorrang vor dem direkt übergebenen Token; Leerzeichen und Zeilenumbrüche entfernt der Entrypoint. Compose reicht diese Variablen durch; die eigentliche Datei bindet ein lokales compose.override.yaml ein, je Runner-Set eine eigene:

services:
  runner:
    volumes:
      - ./secrets/${COMPOSE_PROJECT_NAME}.token:/run/secrets/access_token:ro

Der Runner-Benutzer mit UID 1001 muss die Datei lesen können. Fehlt sie beim Start, legt Docker an ihrer Stelle ein Verzeichnis an; der Entrypoint erkennt das und endet mit 78. Eine zweite Instanz desselben Repositories braucht deshalb neben der verlinkten Env-Datei auch eine verlinkte Token-Datei.

Der Entrypoint prüft Namen und Arbeitsverzeichnispfade, bevor er sie verwendet. Relative Arbeitsverzeichnisse müssen einfache Verzeichnisnamen sein. Absolute Pfade dürfen kein .. enthalten. Neu erstellte Arbeitsverzeichnisse erhalten Modus 700. Bereinigung und Erstellung versuchen zunächst normale Benutzerrechte und verwenden sudo als Rückfall, etwa für von Docker-Jobs hinterlassene Root-Dateien.

Boolesche Werte werden geprüft: true, yes, on und 1 aktivieren eine Option; false, no, off und 0 deaktivieren sie. Andere nichtleere Werte führen zum Abbruch. Ist ein Docker-Socket eingebunden, aber nicht nutzbar, bricht der Start ebenfalls ab. Solche Fehler beendet der Entrypoint mit Exit-Status 78 (EX_CONFIG), Fehler, die ein späterer Versuch beheben kann, mit 1.

Was die Projekt-CI prüft

Der Workflow .github/workflows/ci.yml führt ShellCheck, Hadolint, systemd-analyze verify, einen Image-Bau und drei Testskripte aus. tests/smoke.sh lässt den Entrypoint mit Stellvertretern für config.sh, run.sh und curl vollständig durchlaufen, auch Stopp, Abmeldung, Token-Dateien, Exit-Status und Arbeitsverzeichnisse. tests/compose.sh prüft die gerenderten Compose-Dateien. tests/systemd.sh führt die Befehle der Dienstvorlage selbst aus. Ohne echte GitHub-Zugangsdaten belegen diese Tests keine reale Registrierung.

Für die Aktualisierung dieses Berichts am 2. November 2026 liefen deshalb zusätzlich Live-Tests gegen ein privates Testrepository, auf Docker Desktop mit arm64: Registrierung mit Token in der Umgebung, ein Job mit Checkout und sudo ohne Token in der Jobumgebung, Abmeldung beim Stopp; ephemere Runner über den Befehl der Dienstvorlage, einschließlich ExecStop; Runner im Docker-Override mit runs-on: docker, Docker-Container-Action, Bind-Mount und Service über einen zufälligen Hostport.
